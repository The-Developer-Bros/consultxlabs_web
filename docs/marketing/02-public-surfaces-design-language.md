# The public surfaces' design language: quiet monochrome

This document is the rule set behind the 2026-09-06 refresh of the landing page and the explore surfaces, recorded as prose so that future work on these routes has one place to read before adding a new visual pattern. The decision to adopt this language, and how it relates to the two sibling pull requests that also touch these routes, is recorded in [ADR: quiet monochrome public surfaces](../decisions/2026-09-06-quiet-monochrome-public-surfaces.md). This document is the reference; that one is the record of why.

The app already runs on Sora and a zinc/neutral monochrome token set defined in `app/globals.css`'s `:root`. The rule this refresh applied everywhere it touched is that elegance comes from restraint, hierarchy and consistency, and that type, spacing and hairline borders should carry a page rather than an effect.

## Decoration

Every use of `animate-blob`, a blurred orb `<div>`, `grid-pattern*`, `dot-pattern*`, `diagonal-stripes`, `silver-text`, `gradient-text*`, `glow*`, `chrome-shine`, `spotlight`, `mesh-gradient*`, `metallic-*`, `noise-overlay`, a `bg-gradient-to-*` used as a section's own background, and `backdrop-blur` on a section card is gone from the surfaces this refresh covers. A section's background is one of three flat values: `bg-background` for a light section, `bg-muted/40` for the alternate light tone that used to be a second gradient, and `bg-zinc-950` for a dark section. A hero is allowed exactly one static highlight, and it is always the same element: a `pointer-events-none` absolutely positioned div carrying `bg-[radial-gradient(60%_50%_at_50%_0%,rgba(255,255,255,0.08),transparent)]` across the top 480 pixels. Nothing on these pages is meant to move, glow or shimmer on its own; the one exception is the scroll-triggered reveal described under Motion below.

## Eyebrows, not pill badges

No section label uses `<Badge>` or a Sparkles-icon pill. A section label is a short line of text: `text-xs font-medium uppercase tracking-[0.18em] text-muted-foreground` on a light section, or `text-zinc-500` at the same size and tracking on a dark one. This is the line every `SectionIntro` renders above its heading, and it is the same treatment `ExploreHero`, `PlanHero` and `PlanExpertCard` use for their own labels, so the eyebrow reads as one typographic decision rather than five different implementations of "a small label above a heading".

## Type scale

A hero's `h1` is `text-fluid-5xl font-semibold tracking-[-0.03em] leading-[1.02]`, white on a dark background. A section's `h2` is `text-fluid-3xl md:text-fluid-4xl font-semibold tracking-[-0.02em] text-foreground`. A sub-section or card title is `text-lg font-semibold tracking-tight`. A lede paragraph is `text-base md:text-lg text-muted-foreground leading-relaxed`, capped at `max-w-2xl` so a line never runs the full width of a wide section. Nothing above `text-2xl` uses `font-bold`; `font-semibold` is the ceiling, and any number that appears in a heading or a stat carries `tabular-nums` so a changing figure does not shift its neighbours. A two-tone headline — part `text-foreground`, part `text-muted-foreground` or `text-zinc-400` on dark — is allowed only inside a hero; it is not a device for section headings generally.

## Section intro block

Every section on the landing page and both explore listings opens with the same shape: an eyebrow, then an `h2`, then an optional lede, left-aligned, with `mb-10 md:mb-14` of space below it before the section's content begins. `SectionIntro` (`components/home/SectionIntro.tsx`) is the shared implementation of this block on the landing page; the explore listings compose the same shape from `ExploreHero`'s masthead and each listing's own `SectionHeader`. The block is centered only twice on the whole site: the landing hero and the closing FAQ/CTA. When a section also offers a "see everything" link — "View all experts →" being the canonical example — that link sits on the same row as the heading from `md` up, right-aligned, using `flex flex-col gap-6 md:flex-row md:items-end md:justify-between`, and is styled as plain text rather than a button: `text-sm font-medium text-foreground hover:underline underline-offset-4`.

## Surfaces

A light card is `rounded-2xl border border-border bg-card shadow-elevation-1`. Its hover state adds one step of elevation, a slightly darker border and a small lift: `hover:border-foreground/20 hover:shadow-elevation-2 hover:-translate-y-0.5 transition-all duration-300 ease-out`. No light surface in scope uses `shadow-lg`, `shadow-xl` or `shadow-2xl`; those read as heavier than the rest of the page and were part of what made the old pages feel busy. A dark card is `rounded-2xl border border-white/10 bg-white/[0.04]`, with a hover state of `hover:border-white/20 hover:bg-white/[0.06]`. Hairline dividers are `border-border` on light backgrounds and `border-white/10` on dark ones, and are the only separators these pages use between rows of a list — there is no decorative rule or gradient line anywhere in scope.

## Spacing

A section's vertical rhythm is `py-20 md:py-28`. The landing page's horizontal container is `container mx-auto px-4 md:px-6`; the two explore listings keep their existing wider container, `max-w-[1600px] mx-auto px-4 md:px-8 lg:px-12`, because a listing needs the extra width for its grid and changing it was out of scope. Within a section, a grid of small tiles uses `gap-4` and a grid of cards uses `gap-6`.

## Motion

framer-motion stays on these surfaces, because the owner prefers the feel it gives the page to the bundle savings of removing it. Every scroll reveal on every page uses one preset, factored into `reveal()` in `components/home/SectionIntro.tsx`: fade in and rise 16 pixels, triggered once when the element enters the viewport with an 80px margin, over 500 milliseconds on the curve `[0.16, 1, 0.3, 1]`. A list of siblings staggers by `Math.min(i * 0.05, 0.3)` so a long grid never visibly crawls in from top to bottom. There is no scale reveal, no horizontal reveal, no word-by-word text animation, no card tilt, no cursor-following effect, and no smooth-scroll library anywhere in scope — all five were present in the pages before this refresh, and all five are the direction PR #1213 pursues for the same routes instead, which is why that PR is superseded rather than merged forward (see the ADR). A marquee — the featured-experts strip is the one on the landing page — keeps its `animate-marquee` / `animate-marquee-reverse` travel and gains `hover:[animation-play-state:paused]` on the track so a visitor can stop it to read a card. A hover transform elsewhere is capped at `-translate-y-0.5`, and an icon that nudges on hover moves by `group-hover:translate-x-0.5`.

## Colour

These pages are monochrome. Amber is reserved for one thing — a rating star — and always rendered as `fill-amber-400 text-amber-400`. A semantic token (`success`, `warning`, `destructive`) is used only for a real status a visitor needs to notice, such as a session that is happening now, a plan that has sold out, or an enrollment that has gone through; it is never used decoratively. A feature list's check icon is `<Check className="h-4 w-4 text-foreground" strokeWidth={2} />` rather than the `text-emerald-500` check the old pages used, and nothing this refresh owns keeps a stray `bg-amber-50`, `green-100`, `blue-*` or `gray-*` class. `components/ui/registration-badge.tsx` is shared UI used elsewhere in the product and was deliberately left alone rather than pulled into this monochrome pass.

## Buttons

Every button on these surfaces is the shared `<Button>` from `components/ui/button`. A hero or primary call to action is `size="lg"` with `className="h-12 rounded-xl px-6 text-base"`. On a dark background, the primary button is `bg-white text-zinc-950 hover:bg-zinc-200` and a secondary button beside it is `variant="outline"` with `className="border-white/15 bg-transparent text-white hover:bg-white/10 hover:text-white"`. An arrow icon accompanying a button or link is always lucide's `ArrowRight` at `h-4 w-4`.

## Chips

A taxonomy or metadata chip is `inline-flex items-center rounded-full border border-border bg-background px-2.5 py-1 text-xs font-medium text-muted-foreground`. The one chip on a card that names the primary thing about it — an expert's domain, "Familiarise pick", "Trending" — inverts the treatment to `border-transparent bg-foreground text-background` so it reads as the headline fact among the surrounding chips rather than one item in a flat list. `ConsultantCard`'s `Chip` component is the reference implementation both explore surfaces should match.

## Icon tiles

An icon that anchors a row or a tile sits inside `flex h-10 w-10 shrink-0 items-center justify-center rounded-xl bg-muted text-foreground`, holding a lucide icon at `h-5 w-5` with `strokeWidth={1.75}`. There is no gradient tile and no black square behind a section-header icon anywhere in scope; `TaxonomyGrid`'s tile and `AudienceSplitSection`'s feature icons both use this exact shape.

## Honesty

A page never renders content that no data produced. If a field is empty, the element that would have shown it is omitted rather than filled with placeholder text. This is why `AboutSection` disappears entirely from a profile with nothing filled in rather than printing a templated bio, why an expert card with no headline shows no headline row, and why the fictional `SUCCESS_STORIES`, the stale `UPCOMING_EVENTS`, `TRUST_BADGES` and `SatisfiedTestimonial` no longer exist. The rule generalizes past this refresh: the next time a section needs a fallback for missing data, the fallback is to not render the section.

## Preservation

None of the above touches behaviour. Every `href`, `aria-*` attribute, keyboard handler, `sizes` prop on a filled `next/image`, `memo` boundary, hook, data prop, anchor `id` and its `scroll-mt-*` offset, Suspense or skeleton boundary, and every `revalidate` / `force-dynamic` / `withBuildTimeRetry` export was carried through unchanged — a Jest test greps the page files for the last group and fails if one goes missing. Data loaders, hooks and API calls were not touched by this refresh at all; every change described here is confined to JSX layout and class names.

## Component map

### Landing page (`/`)

`app/page.tsx` composes ten sections, down from sixteen. In source order: `HeroSection` (dark, the fluid-5xl headline and the one static highlight), `TrustedBySection` (a light hairline logo strip), `FeaturesSection` (the four session formats plus the trimmed platform-capabilities list beneath them), `CategoriesSection` (browse-by-domain cards driven by real per-domain counts), `FeaturedExpertsSection` (the pausable marquee), `BenefitsSection` ("why Familiarise"), `TestimonialsSection` (real session reviews, dark), `HowItWorksSection`, `AudienceSplitSection`, and `FAQSection`. `SectionIntro` (`components/home/SectionIntro.tsx`) is the shared eyebrow/heading/lede block every one of these sections opens with, and it also exports the `reveal()` and `staggerDelay()` helpers that give every section the same scroll animation. `AudienceSplitSection` (`components/home/AudienceSplitSection.tsx`) is new: it replaces the old `EnterpriseSection` and `BecomeExpertSection`, putting the organisation-facing pitch (dark card) and the expert-facing pitch (light card) side by side in one row instead of two full-width bands. Six landing section files were deleted outright because the content behind them was fabricated or stale: `SuccessStoriesSection.tsx`, `UpcomingEventsSection.tsx`, `TrustBadgesSection.tsx`, `PlatformFeaturesSection.tsx`, `BecomeExpertSection.tsx` and `EnterpriseSection.tsx`, along with the `SatisfiedTestimonial.tsx` component `SuccessStoriesSection` had used.

### Explore experts (`/explore/experts`)

`app/explore/experts/page.tsx` and `ExpertsInteractiveContent.tsx` compose `ExploreHero` (`app/explore/components/ExploreHero.tsx`) for the dark masthead, `TaxonomyGrid` (`app/explore/components/TaxonomyGrid.tsx`) for the "browse by domain" tile grid, `SegmentedControl` (`app/explore/components/SegmentedControl.tsx`) for the affiliation and grid/list toggles, and `SectionHeader` (`app/explore/components/SectionHeader.tsx`) above each results block. `ConsultantCard` (`app/explore/experts/components/ConsultantCard.tsx`) is the result row: a two-column card with the expert's identity, taxonomy chips and mentorship-plan pricing on one side and the profile/trial/book actions on the other, and it renders a headline only when the expert has written one. `DomainGrid.tsx` was deleted; `TaxonomyGrid` replaced it (and its programs-side twin, `CategoryGrid.tsx`) with one implementation shared by both listings.

### Expert profile (`/explore/experts/[consultantId]`)

`ExpertProfileClient.tsx` lays the page out as a light main column — `ProfileHeader`, `AboutSection`, `ExperienceSection`, `ConsultantAvailability`, then `ClassesAndWebinars` and `ReviewsSection` below the fold — beside one anchored dark surface, the booking panel rendered by `ExpertPricing`. That panel is the only dark card left on the page, kept deliberately as the one thing the page wants a visitor to act on. The 4:3 portrait that used to sit above the booking panel was removed because it duplicated the photo already shown in `ProfileHeader`. `AboutSection` (`app/explore/experts/[consultantId]/components/AboutSection.tsx`) now renders only what the expert actually wrote — an about paragraph, a mentoring-style paragraph, skill tags, tools — and disappears entirely when none of those exist, instead of filling gaps with a templated bio.

### Explore programs (`/explore/programs`)

`app/explore/programs/page.tsx`, `ProgramsInteractiveContent.tsx` and `ProgramsExploreSkeleton.tsx` share the same `ExploreHero`, `SegmentedControl`, `TaxonomyGrid` and `SectionHeader` components the experts listing uses, so the two listings read as one family rather than two independently designed pages. `ProgramCard.tsx` and `FeaturedCarousel.tsx` carry the same card and chip treatment as `ConsultantCard`. The programs-side `CategoryGrid.tsx`, `FilterChips.tsx` and `SectionHeader.tsx` were deleted in favour of the shared `app/explore/components/` versions.

### Plan detail pages (`/explore/programs/plans/{classes,webinars,consultations,subscriptions}/[id]`)

All four plan types share four new components under `app/explore/programs/plans/components/`. `PlanHero.tsx` is the dark title band: a class or webinar plan gets a cover image under a scrim, a consultation or subscription plan gets the same band on a plain dark stage, so all four read as one product family rather than two different layouts. `PlanExpertCard.tsx` is the sidebar card naming the instructor, host, expert or mentor behind the plan, rendering their real headline and experience or nothing at all — this is the component that removed the hardcoded "An experienced professional dedicated to sharing knowledge and expertise." line. `PlanDetailBody.tsx` composes the content column — description, target audience, what's included, learning outcomes, curriculum, prerequisites, materials, FAQ, topics — with every section returning `null` when its data is empty, so a sparsely authored plan renders a short page instead of a run of empty bordered cards. `FeatureItem.tsx` is the small icon-label-value cell used in each plan's facts grid under the hero. The four page-level `*Details.tsx` files (`ClassDetails`, `WebinarDetails`, `ConsultationDetails`, `SubscriptionDetails`) keep whatever is genuinely per-type — the hero's specific fields, the facts grid's specific rows, the booking sidebar — and compose these four shared components for everything else, including the removal of the webinar page's "Platform: Zoom" fallback now that every session runs in the product's own video room.

## What is out of scope and still uses the old utilities

This refresh covered five surfaces: the landing page, both explore listings, the expert profile, and the four plan detail page types. It deliberately did not touch `/enterprise` (`app/enterprise/_components/EnterpriseSections.tsx`), `/use-cases` (`app/use-cases/UseCaseSections.tsx`), `/explore/community`, `/explore/enterprise/organisations`, the become-an-expert page (`app/(pages)/become-an-expert/page.tsx`), or the site-wide `components/Footer.tsx`. Most of these still reference `animate-blob` and the `grid-pattern*` utilities, which is exactly why those utilities were left in `app/globals.css` rather than deleted along with the fifty-nine that were removed — deleting them now would break pages nobody has redesigned yet. Bringing any of these surfaces onto the language documented above is future work, and whoever picks it up should read the ADR's Consequences section first, since it names this same boundary.
