# Support chat turn loss, and the sweep that followed

**Date:** 2026-08-29 · **Branch:** `fix/support-feedback-review-sweep` · **Issue:** #705 · **Scope:** the support drawer in both scopes, the ticket queue behind it, the private CSAT rail, and the public review corpus.

This entry records a single reported defect, the eight independent causes that turned out to sit behind it, and the schema that had to change before any of them could be fixed properly. It is written so that nobody has to re-derive the diagnosis from the diff, and so that the two audit claims which did not survive verification are not investigated a second time.

## The reported symptom

While chatting in the support drawer, the user's own message or the bot's reply sometimes did not appear. The report was deliberately vague about which of the two went missing and about when, and that vagueness turned out to be accurate rather than unhelpful: there was no single failure to find. Depending on which drawer the user was in, which control they pressed, and how long they had been sitting in the conversation, a different mechanism swallowed a different part of the exchange. Some of the causes lose the user's own bubble, some lose the bot's reply, some lose both, one silently reorders them so that the answer can render above the question, and one stops the composer from accepting input at all without ever saying so.

## The eight causes

The table below lists each cause with the file that now holds its remedy, so that a reader can open the code alongside this entry. The prose after it explains each diagnosis; the remedies are collected in the following section.

| # | Cause in one line | Where |
|---|---|---|
| C1 | The platform sheet collected the pressed chip's label and never rendered it, so an option tap produced no user bubble at all. | `components/support/PlatformSupportSheet.tsx:156` |
| C2 | The `DOCUMENTS` intent was offered by the `GET` on every appointment and rejected by the `POST`'s hand-transcribed enum, so every press returned a 400. | `schemas/enums.ts:23`, `app/api/appointments/[appointmentId]/support/route.ts:32` |
| C3 | Free text typed at a prompt got no reply, because the server suppressed the re-presented prompt and the client discarded the messages the server did return. | `lib/support/flow-walk.ts:117`, `lib/support/service.ts:246` |
| C4 | There was no optimistic echo in the appointment drawer, so a turn needed two serial round trips before anything at all rendered. | `components/support/SupportThreadSheet.tsx:185` |
| C5 | `turnPending` latched on `turn.isSuccess && isFetching`, so the fifteen-second poll disabled the composer permanently after the first turn. | `components/support/SupportThreadSheet.tsx:292` |
| C6 | Neither drawer scrolled to the newest bubble, so past the drawer height every reply landed below the fold. | `components/support/SupportThreadSheet.tsx:297`, `components/support/PlatformSupportSheet.tsx:280` |
| C7 | `SupportMessage` had no ordering tiebreak, while the user's turn and the bot's reply share one transaction and therefore one timestamp. | `prisma/schema.prisma:476`, `lib/support/message-seq.ts:23` |
| C8 | An unrecognized option id persisted nothing and returned a 200, so the turn looked successful and left no trace. | `lib/support/flow-walk.ts:118`, `lib/support/service.ts:252` |

### C1 — the pressed chip's label was collected and then thrown away

In the platform sheet the option buttons already passed the label of the chip the user had pressed into the mutation, as a client-only variable that the request body deliberately stripped out. The variable's own docstring said "Client-only label of the pressed chip — see onSuccess. Never sent." The `onSuccess` handler it pointed at rendered `vars.userMessage` and nothing else. Typing free text therefore produced a user bubble, and pressing a chip produced none, so the entire platform transcript read as a monologue by the bot in which the user's side of every branch was invisible. The label was being carried the whole way and then dropped one line before it would have been used.

### C2 — an intent the catalogue offered and the turn route refused

`documentsFlow` is defined at `lib/support/flows.ts:482` and carries no `available` gate, which means the `GET` that builds the server-gated intent list offered "Session materials" on every appointment regardless of stage or role. The `POST` on the same route validated the incoming category against a `z.enum` transcribed by hand, and that transcription had lost `DOCUMENTS`. The same list had been transcribed into two further route files, and every copy was missing the same member. Pressing the chip therefore failed validation before any flow ran, so the request returned a 400 with a `VALIDATION_FAILED` envelope, nothing was written, nothing rendered, and the only signal the user received was a toast.

### C3 — free text at a prompt was answered by silence

When the walk reached a `PROMPT` node and the input matched none of its options, `walkFlow` re-presented the identical prompt. That is defensible as a pure transition, but two layers downstream conspired against it. The service treated a turn whose cursor had not moved as a re-present and suppressed the bot's messages so that one press could not append two identical bubbles. The client, in turn, discarded the messages the server did return and waited for a refetch. Between the two, a user who typed a sentence at a prompt saw their own message persist and then saw nothing come back, which is the exact shape of the original report.

### C4 — nothing rendered until two round trips had completed

The appointment drawer's mutation only invalidated its query on success. A press therefore showed nothing until the `POST` had returned and a follow-up `GET` had also returned and been applied. On a warm connection that is a visible stutter; on a cold serverless instance it is a long silent gap that reads unambiguously as the tap having missed, which is precisely what prompts a user to press the chip a second time.

### C5 — the composer latched itself off after the first successful turn

The drawer computed `turnPending` as `turn.isPending || (turn.isSuccess && isFetching)`. That guard was added for a real reason: a second `POST` landing in the refetch window, after `isPending` had flipped false but before the refetch had swapped the options, produced a double bubble. The trouble is that the thread also polls every fifteen seconds while the sheet is open, so `isFetching` becomes true on a schedule forever, and `turn.isSuccess` stays true forever once any turn has succeeded. The conjunction is therefore permanently satisfiable from the first successful turn onward, and every chip and the send button spent most of the conversation disabled with no explanation on screen.

### C6 — the newest bubble was below the fold

Both transcripts are plain overflow containers with no scroll management of any kind. Once a conversation grew past the height of the drawer, every new message — the user's echo and the bot's reply alike — was appended out of view. Nothing was missing from the DOM, and to the user nothing had happened.

### C7 — the answer could sort above the question

`SupportMessage` was ordered by `createdAt` alone. The user's turn and the bot's reply are written inside one transaction, and Postgres `CURRENT_TIMESTAMP` is transaction start time, so both rows can carry a byte-identical timestamp. With equal keys the order falls to whatever the planner returns, and the reply can render above the message that prompted it. Adding the primary key as a tiebreak would only have made the wrong answer deterministic rather than correct, because the id is a random uuid and would put the reply first roughly half the time.

### C8 — a turn that recognized nothing reported success

The unrecognized-option path combined with the re-present suppression to produce a `200` response carrying messages that were never persisted and, once the client discarded them, never displayed. Nothing distinguished that outcome from a successful turn at any layer: not the status code, not the response body, and not the stored transcript. A stale option id from a drawer that had been left open, a double submit, and genuinely unparseable free text all landed in the same silent hole.

## What was done about each

**C1.** The platform sheet now echoes the user's turn from `onMutate`, before the request is sent, using `vars.userMessage ?? vars.chosenLabel` so that a chip press and typed text take the same path. The optimistic bubble is rendered at reduced opacity until the server confirms it, and `onError` removes it, because a bubble that stays on screen after the turn failed claims that something was said which the server never received. Every locally-held message gained an explicit id, since this scope persists nothing and an array index reuses DOM nodes positionally rather than identifying a bubble that is later replaced in place.

**C2.** The category and status lists now have exactly one definition, in `schemas/enums.ts`, and the three routes that had transcribed them import it. The definition is guarded in both directions: a `satisfies readonly SupportThreadCategory[]` assertion fails to compile on a typo or a removed member, and `__tests__/support/intent-offer-accept-parity.test.ts` runs in the node environment and fails if Prisma gains a member that the list has not. The test asserts the invariant rather than the single symptom, so the next flow added with a fresh category cannot reintroduce the same divergence. The registry, not the schema, remains the authority on which intents are *offered*; the schema's only job is to accept anything the registry can emit.

**C3 and C8.** `walkFlow` no longer re-presents the prompt verbatim. It answers with a distinct nudge that names the escape hatch explicitly — "type agent to reach a person", which is a recognised human keyword — and carries the same options in its metadata so the chips stay live and the cursor stays put. Because the reply is no longer a duplicate of the prompt, there is nothing left to suppress, and the service now persists every message it emits, including this one. The walk result also carries a new `unrecognized` flag so that a caller can tell "the cursor did not move" from "the turn made progress" without comparing node ids. `__tests__/support/service.test.ts` was rewritten around the new behaviour: it asserts that exactly one bubble is written, that it is a `BOT` message which is not a verbatim repeat, and that its metadata still carries both the options and the node id.

**C4.** The appointment drawer gained the same optimistic echo, written into the react-query cache rather than into local state, with the previous cache value returned from `onMutate` so that `onError` can roll the whole thing back. On success the server's own reply is merged into the cache directly instead of the drawer only invalidating and waiting: an invalidation makes the bot's answer wait for a second round trip, and a poll resolving inside that window can land pre-turn rows on top of it. The confirming refetch still runs behind the merge and replaces the optimistic bubbles with the persisted rows, which carry identical bodies.

**C5.** `turnPending` is now `turn.isPending` and nothing else. The double-bubble race the old guard existed to prevent is closed at its actual source instead: the poll is suspended while a turn is in flight, so a refetch can no longer resolve on top of the optimistic write. That makes the poll bounded on four sides rather than three — only while the sheet is open, never once the thread is settled, never in a background tab, and never during a turn.

**C6.** Both drawers now hold a ref on a sentinel element at the end of the transcript and scroll it into view whenever the sheet is open, the message count changes, or a turn starts or finishes. Both also gained a typing indicator while a turn is in flight, so the gap between the user's echo and the bot's reply is visibly a wait rather than a failure.

**C7.** `SupportMessage` gained a `seq` column and every read path was moved onto a shared `MESSAGE_ORDER` constant. The details are in the schema section below.

Two further defects were found in the same paths and fixed alongside them, because leaving them would have made the drawer's behaviour incoherent in a different way. The chips are now taken from the message sitting at the server's cursor rather than from whichever `BOT` message happens to be last, since those two can drift and a chip whose option id the server no longer recognises spends a whole round trip to answer "I didn't catch that". And pressing an intent chip is now recorded as the user's first message: the walk can only name an option it matched, and the entry presentation matches nothing, so the stored transcript used to open with a bot prompt and no record of what had been asked for — which is what a staff member saw in the back-office inbox on every escalated thread.

## The schema additions, and why each exists

Every column below is additive and nullable or defaulted, so the change is compatible with the pre-MVP freeze and no backfill is owed. The groups are described in the order they appear in `prisma/schema.prisma`.

**`SupportTicket.referenceNumber` (line 283) and the `SupportTicketCounter` model (line 362).** A uuid cannot be read back over a phone line or quoted in an email subject, and the two staff surfaces had each invented their own truncation — one took the first eight characters and the other the last, so the two screens named the same ticket differently — while the user was shown no identifier at all. The counter is keyed by year and allocated with an upsert that compiles to `INSERT … ON CONFLICT DO UPDATE … RETURNING`, so concurrent ticket creation queues on one row and each caller receives a distinct number. The column is `@unique`, which turns any residual duplicate into a `P2002` to retry rather than two tickets quietly sharing a handle. It is nullable because it is minted forward-only: a unique index permits unlimited nulls, so tickets that predate the counter keep their uuid and every surface falls back to the old truncation for them.

**`SupportTicket.assignedTo` (line 308).** The assignee was a bare `String`, so it could name a user who no longer exists and the ops queue could not render a name without a second query. It is now a real relation with `onDelete: SetNull`, never `Cascade`, because a staff departure must not delete tickets.

**The eight SLA columns on `SupportTicket` (lines 320 to 333) and their two indexes (lines 352 and 353).** These are `ackDueAt`, `acknowledgedAt`, `resolutionDueAt`, `resolvedAt`, `closedAt`, `firstAgentReplyAt`, `awaitingUserSince` and `pausedMs`. The deadlines are stored at intake rather than derived at read time, for the same reason `Appointment.cancellationPolicySnapshot` is stored: a later change to the policy table must not retroactively re-date an open ticket's breach. There is deliberately no `slaState` column, because every state is derivable from these stamps plus the current time and a stored one would go stale between cron runs. `firstAgentReplyAt` is separate from `acknowledgedAt` because an automated acknowledgement satisfies the latter and only the former predicts CSAT. The two indexes exist so that "unacknowledged and past due" and "unresolved and past due" are index scans rather than a scan of the whole queue.

**`AppointmentSupportThread.messageSeq` (line 445) and `SupportMessage.seq` (line 476).** This pair is the remedy for C7. The counter lives on the thread row, which every message write already touches to bump `lastMessageAt`, so the row lock it takes costs nothing extra and is exactly the serialization point between a user typing on their phone and an agent replying on desktop. Rows written before the column existed keep `0` and sort first, which is chronologically right because they all predate it. `@@index([threadId, seq])` at line 487 serves the new ordering.

**`SupportMessage.authorUserId` (line 483).** An `AGENT` row used to record no author, so an escalated transcript could not say which staff member had replied. It is null for `USER`, `BOT` and `SYSTEM` rows, where the thread's own `userId` identifies the user side, and null on `AGENT` rows written before the column, where it honestly records "no longer known". The delete behaviour is `SetNull` for the same reason as the assignee, and the column carries its own index because Postgres does not index a foreign key for you and the `SetNull` scans by it.

**The `SupportFlowOutcome` model and the `SupportFlowOutcomeKind` enum (lines 508 and 541).** One row is written per terminal support turn in both scopes. This is what makes the deflection rate answerable; the reasoning and the caveat are in the [support hub document](support-hub.md#deflection-what-fraction-the-tree-actually-resolves). The model is deliberately not derived from thread status, because a thread is reused across intents and its final status describes the last thing that happened to it rather than each flow run, and because the platform scope has no thread to read at all. It carries no message bodies: it is a counter, not a transcript.

**`AppointmentFeedback.raterRole` and the `AppointmentFeedbackRole` enum (lines 569 and 579).** The CSAT `POST` authorizes any participant, so without this column a consultant's private rating of their own session was indistinguishable from an attendee's and landed in the org quality average. The column is nullable and never backfilled, because rows written before it cannot be attributed and asserting `CONSULTEE` over them would re-admit exactly the self-ratings being excluded. The org aggregate therefore filters *on* `CONSULTEE` rather than excluding `PROVIDER`, so unknown provenance fails closed. The index at line 576 became `[organizationId, raterRole, createdAt]` because the aggregate now filters `raterRole` before the date range, which leaves the old two-column index without a usable prefix.

**`ConsultantProfile.publishedRating`, `ratingUnitCount`, `reviewCount` and `ratingAggregatedAt` (lines 2694 to 2705), plus `@@index([publishedRating])` at line 2814.** The existing `rating` column stays as the raw mean and remains the internal number. The published score is a separate column so that a null can mean "suppressed" without also meaning "zero", and so that explore's sort and the minimum-rating filter read the same value the profile page displays. `reviewCount` also retires the trending sort's `{ reviews: { _count: "desc" } }`, which counted soft-deleted rows because Prisma cannot filter a relation `_count` inside `orderBy`, so a moderated-away review kept pushing its consultant up the list. `ratingAggregatedAt` exists purely for a drift audit: it finds profiles whose aggregates predate their newest review without recomputing every profile to find out.

**`ConsultantReview.appointmentId` and `ratingUnitId` (lines 2876 and 2888), the reply columns at 2894 to 2896, and the unique swap at line 2913.** These carry the review-scoring model, which is recorded in full as [ADR 25](../enterprise/70-design-decisions/25-per-session-reviews-and-published-score.md). In summary, `appointmentId` is what makes "verified booking" a fact rather than a claim and is what lets a repeat client review each session instead of being locked out forever; `ratingUnitId` is denormalized at write time because Prisma `groupBy` can only group on the model's own scalars; and the reply columns are columns rather than a table because there is one reply per review and every read of a review already loads its row, with `replyDeletedAt` kept separate from the review's own `deletedAt` so that staff can remove an abusive reply without erasing the consumer review beneath it. The unique moved from `[consultantProfileId, consulteeProfileId]` to `[appointmentId, consulteeProfileId]`. It is deliberately not partial on `deletedAt`, because a moderation-removed review must not free the slot for the same person to re-post it.

**One sidecar index, `consultant_review_legacy_pair_key` in `prisma/sql/check-constraints.sql`.** Legacy review rows carry a null `appointmentId`, and Postgres treats a null key column as distinct, so the new unique is permissive for exactly the rows that were never gated per session — the old one-review-per-pair rule would silently lapse for them. The partial unique preserves that rule for the legacy band only and expires with the pre-MVP reset once no nulls remain. It cannot fail to build, because the constraint it replaces already guarantees those pairs are unique today.

One operational step goes with the push, and it is deliberately not a migration. The three new rating columns arrive null and zero, and null means "suppressed", so until something recomputes them every consultant's published score is hidden. `npm run db:recompute-ratings` (`scripts/db/recompute-consultant-ratings.ts`) walks every profile and calls the same `recomputeConsultantRating` that every review mutation calls. It is ordinary application code rather than a backfill: idempotent, re-runnable, `--dry-run`-capable, touching no DDL, and depended on by nothing in the schema. It wraps each profile in the same Serializable-with-retry used by the mutation paths, so a review landing mid-run cannot lose-update the average it writes.

While adding the sidecar index, the sidecar assertion script turned out to be under-asserting. `scripts/db/assert-sidecar-applied.ts` excluded staged objects by splitting the file on the "STAGED FOR THE PRE-MVP RESET" banner, but active SQL sits below that banner too, so `appointment_doc_thread_version_unique` and `onboarding_draft_payload_size` had never been asserted against any live database. What actually marks an object as staged is that it is commented out, so the script now strips comment lines instead, and its index-name regex now skips an optional `IF NOT EXISTS` that it had previously been capturing as the literal index name `IF`. `__tests__/payments/idempotency-minting.test.ts` was changed to pin this behaviourally rather than by matching the old implementation string.

## Two handoff claims that were checked and found stale

Both of the following came in with the handoff, both were checked against the current tree, and neither is actionable. They are recorded here so that nobody spends the investigation again.

**Audit item S5 — the ungated fallback chip list — was already deleted.** The claim was that `SupportThreadSheet.tsx` falls back to a hardcoded intent list when the server-gated fetch fails, and that the fallback is stage-blind by construction, so it offers "Cancel & refund" on a session that has already happened and "The other party didn't show" on one that has not started. That was true, and it was fixed on 2026-08-27 in commit `1767ef8f`, whose message describes the deletion in those terms. On this branch the only thing that changed in that region is the comment block above `availableIntents`, which was compressed from a long historical narrative into a statement of the current rule. There is no fallback list left to remove.

**Audit item D6 is wrong as worded, because `SupportSurface.tsx` passes no `feedbackHref`.** The claim was that the support hub renders a broken "Leave feedback" link. `SupportHub` does accept an optional `feedbackHref` prop and does render a link when it is given one, but `components/dashboard/shared/support/SupportSurface.tsx:36` mounts `<SupportHub profileId={profileId} />` with no such prop, so no link renders from that surface at all. The two dashboard pages that do pass the prop — `app/dashboard/consultant/[consultantId]/(features)/support/page.tsx:19` and `app/dashboard/consultee/[consulteeId]/(features)/support/page.tsx:19` — point at `/dashboard/consultant/<id>/feedback` and `/dashboard/consultee/<id>/feedback`, and both of those route segments exist. Nothing here is broken, and the item should be closed rather than re-triaged.
