# Schema reference: the support tables

This page lists every column the support subsystem added or changed, model by model, with the reasoning that is too long for a schema comment. Every change is additive and either nullable or defaulted, so each is compatible with the pre-MVP freeze and none needs a backfill. The private rating table is documented in [`docs/feedback/03-schema-reference.md`](../feedback/03-schema-reference.md) and the public review tables in [`docs/reviews/06-schema-reference.md`](../reviews/06-schema-reference.md).

## `SupportTicket`

The table below lists the columns and indexes #705 and the #support-hub work added to the ticket, and why each exists.

| Column or index                                                                                                                      | Why it exists                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `organizationId?` + `@@index([organizationId, status])`                                                                              | The ops queue is filterable by customer organisation.                                                                                                                                                                                                                                                                                       |
| `lastMessageAt?`                                                                                                                     | "Latest activity first": `updatedAt` does not move on message inserts, so the inbox sort needs its own clock. Every visible message write bumps it inside the same transaction.                                                                                                                                                             |
| `referenceNumber?` (`@unique`, `VarChar(20)`)                                                                                        | The speakable `FAM-<YYYY>-<SEQ6>` handle. Nullable and minted forward-only: a unique index permits unlimited nulls, so pre-counter tickets keep their uuid. See [03-ticket-references-and-sla.md](03-ticket-references-and-sla.md).                                                                                                         |
| `assignedTo` relation (`SetNull`) replacing the bare `assignedToId` string                                                           | A bare string could name a user who no longer exists, and the queue could not render a name without a second query. `SetNull`, never `Cascade`: a staff departure must not delete tickets.                                                                                                                                                  |
| `ackDueAt`, `acknowledgedAt`, `resolutionDueAt`, `resolvedAt`, `closedAt`, `firstAgentReplyAt`, `awaitingUserSince`, `pausedSeconds` | The SLA clocks, stored at intake so a policy change cannot re-date an open ticket's breach. There is deliberately no `slaState` column: every state derives from these stamps plus the current time, and a stored one would go stale between cron runs. `pausedSeconds` is seconds because an `Int` of milliseconds overflows at 24.8 days. |
| `@@index([acknowledgedAt, ackDueAt])` and `@@index([resolvedAt, resolutionDueAt])`                                                   | "Unacknowledged and past due" and "unresolved and past due" become index scans rather than a scan of the whole queue.                                                                                                                                                                                                                       |

## `SupportTicketCounter`

One row per calendar year, keyed by the year, holding the last allocated sequence. The allocator upserts it inside the ticket's own transaction; the mechanics are in [03-ticket-references-and-sla.md](03-ticket-references-and-sla.md).

## `AppointmentSupportThread`

The table below lists the thread's added columns.

| Column or index                                       | Why it exists                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `lastMessageAt?` + `@@index([status, lastMessageAt])` | The same activity clock as the ticket, and the index the inbox sort needs.                                                                                                                                                                                                                                                                                                           |
| `messageSeq`                                          | The per-thread sequence allocator. It lives on the thread row, which every message write already touches to bump `lastMessageAt`, so the row lock it takes costs nothing extra and is exactly the serialization point between a user typing on their phone and an agent replying on desktop. Rows written before the column keep `0` and sort first, which is chronologically right. |

## `SupportMessage`

The table below lists the message's added columns.

| Column or index                                         | Why it exists                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `seq` + `@@index([threadId, seq])`                      | A strict per-thread total order. The user's turn and the bot's reply are written in one transaction, and Postgres `CURRENT_TIMESTAMP` is transaction start time, so `createdAt` alone cannot order them. Every read uses `MESSAGE_ORDER` from `lib/support/message-seq.ts`.                                                    |
| `authorUserId?` (`SetNull`) + `@@index([authorUserId])` | Which staff member wrote an `AGENT` message. Null for `USER`, `BOT` and `SYSTEM` rows, where the thread's own `userId` identifies the user side, and null on `AGENT` rows written before the column, where it honestly records "no longer known". Postgres does not index a foreign key for you and the `SetNull` scans by it. |

## `SupportFlowOutcome` and `SupportFlowOutcomeKind`

The deflection counter. One row per terminal support turn in both scopes, with no message bodies. The table below lists its columns.

| Column or index                                                        | Why it exists                                                                                                                                                                                                                                                                                     |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scope` (`VarChar(32)`)                                                | `"APPOINTMENT"` or `"PLATFORM"`. A string rather than an enum, because the scope is a reporting dimension rather than a state machine, and a third intake surface should not need a migration to be counted.                                                                                      |
| `flowKey`                                                              | The flow registry key: a `SupportThreadCategory` for appointment scope, a `PlatformFlowId` for platform scope.                                                                                                                                                                                    |
| `terminalNodeId?`, `reason?`                                           | The terminal reached and its machine-readable `reason`, the same value that types an escalated ticket. Both null when the walk failed safe with no terminal.                                                                                                                                      |
| `outcome`                                                              | `RESOLVED` (the tree answered and the user did not need a person) or `ESCALATED` (the turn handed off to a human).                                                                                                                                                                                |
| `userId`, `organizationId?`                                            | Attribution. The user cascades; the organisation is `SetNull`.                                                                                                                                                                                                                                    |
| `helpfulRating?` (`SmallInt`)                                          | The tree's own CSAT, bound to the flow terminal because a `RESOLVED` outcome writes no ticket. `NULL` means not asked or not answered and must never be read as a 1; the reasoning is in [04-deflection-and-support-csat.md](04-deflection-and-support-csat.md). No prompt writes it yet (#1546). |
| `@@index([createdAt, outcome])`, `@@index([flowKey, outcome])`         | The deflection rate itself, and the per-flow breakdown behind it.                                                                                                                                                                                                                                 |
| `@@index([userId, createdAt])`, `@@index([organizationId, createdAt])` | The re-contact signal the deflection rate has to be read beside, and the per-organisation view of it.                                                                                                                                                                                             |

## Applying the schema

Every index above requires `npm run db:push` on each environment, because a schema-only merge does not create it; `db:push` chains the SQL sidecars and then asserts them. `npm run db:preflight` runs first and refuses any destructive statement, which is described with the rest of the deployment order in [`docs/reviews/07-deployment-and-deferred-work.md`](../reviews/07-deployment-and-deferred-work.md).
