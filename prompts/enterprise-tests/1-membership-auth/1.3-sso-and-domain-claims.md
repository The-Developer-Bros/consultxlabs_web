## SSO.1: Create SAML provider

```js
() => fetch("/api/organizations/<wipro-id>/sso", {
  method: "POST", credentials: "include",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({
    providerId: "test-sso-okta",
    issuer: "https://test-sso.okta.com",
    samlConfig: {
      entryPoint: "https://test-sso.okta.com/sso/saml",
      cert: "<base64-cert>",
      callbackUrl: "" // server fills via deriveAcsUrl
    }
  })
}).then(async r => ({ status: r.status, body: await r.json() }))
```

### Assertions
- `status === 201`
- `body.data.callbackUrl` matches `deriveAcsUrl(orgSlug)` shape
  (typically `https://<host>/api/auth/sso/saml/<providerId>/callback`).
- DB `ssoProvider` row exists.
- Audit: `SSO_PROVIDER_CONFIGURED`.

## SSO.4: Enforce SSO + non-SSO sign-in

Update org settings to `enforceSso = true` with the domain claim from
SSO.3 (or via the SSO provider's `allowedEmailDomains`).

Attempt regular email-password sign-in for `someone@test-sso.example`
without going through the SSO provider.

### Assertions
- The session is rejected via `lib/sso/enforce-session.ts:shouldRejectSession`.
- API returns 403 or the session cookie is rotated and the user lands on
  a "Use SSO to sign in" page.

Edge case: a `users` row whose email matches the enforced domain but
who has no `Account` linked to any `SsoProvider.providerId` is the
exact case `shouldRejectSession` is designed for. Verify by reading the
helper's branch logic at `lib/auth.ts:497`.

## SSO.6: SAML cert validation — garbage cert rejected at registration

POST a SAML provider with a fake cert (the kind that used to crash
BetterAuth at signin):

```js
() => fetch("/api/organizations/<wipro-id>/sso/providers", {
  method: "POST", credentials: "include",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({
    providerId: "test-bad-cert",
    domain: "wipro-test-2026.com",
    issuer: "https://test-sso.okta.com",
    providerType: "saml",
    samlConfig: {
      issuer: "https://test-sso.okta.com",
      entryPoint: "https://test-sso.okta.com/saml/sso",
      cert: "MIIBkTCB+wIJAJHoKtest1234567890==",
    },
  }),
}).then(async r => ({ status: r.status, body: await r.json() }))
```

### Assertions
- `status === 400`
- `body.error` or `body.detail.fieldErrors.cert` mentions "Invalid X.509 certificate"
- No `ssoProvider` row created:
  ```sql
  SELECT count(*) FROM "ssoProvider" WHERE "providerId" = 'test-bad-cert';
  -- Expected: 0
  ```

**Audit Phase A.2.** Pre-fix, BetterAuth's underlying SAML adapter
crashed at first signin with
`TypeError: Cannot read properties of undefined (reading 'metadata')`.
Now the bad cert is rejected at the schema layer.

## SSO.7: Domain ownership — unverified-domain provider registration → 422

Pre-condition: claim a domain but do NOT verify it.

```js
() => fetch("/api/organizations/<wipro-id>/domain-claims", {
  method: "POST", credentials: "include",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({ domain: "test-unverified-domain.example" }),
})
```

Then attempt to register an SSO provider for the unverified domain
(with a valid cert this time — get one from any IdP test fixture or
generate via `openssl req -x509 -nodes -days 365 -newkey rsa:2048
-keyout /tmp/k.pem -out /tmp/c.pem`):

```js
() => fetch("/api/organizations/<wipro-id>/sso/providers", {
  method: "POST", credentials: "include",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({
    providerId: "test-unverified",
    domain: "test-unverified-domain.example",
    issuer: "https://idp.example.com",
    providerType: "saml",
    samlConfig: { issuer: "https://idp.example.com", entryPoint: "https://idp.example.com/saml", cert: "<valid PEM>" },
  }),
})
```

### Assertions
- `status === 422`
- `body.code === "DOMAIN_NOT_VERIFIED"`
- No `ssoProvider` row created.

Repeat with a domain not even claimed:
- `status === 422`
- `body.code === "DOMAIN_NOT_OWNED"`

**Audit Phase B.3.** The pre-fix behaviour was "defended by accident" —
the runtime auth hook would silently never honour the unverified
provider, but registration appeared to succeed; the org admin saw a
provider that mysteriously didn't fire.

## SSO.8: JIT default role — PATCH `defaultRoleForAutoJoin: "OWNER"` → 400

```js
() => fetch("/api/organizations/<wipro-id>/sso", {
  method: "PATCH", credentials: "include",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({ defaultRoleForAutoJoin: "OWNER" }),
}).then(async r => ({ status: r.status, body: await r.json() }))
```

### Assertions
- `status === 400`
- `body.detail.fieldErrors.defaultRoleForAutoJoin` mentions LEARNER
- DB: `OrganizationSSOSettings.defaultRoleForAutoJoin` unchanged

Repeat with `MAINTAINER`, `MANAGER`, `EXPERT`, `SUPPORT` — all 400.
Only `defaultRoleForAutoJoin: "LEARNER"` (or omitting the field) is
accepted.

**Audit Phase A.1.** Pre-fix, setting `OWNER` made the first SSO user
co-owner instantly. Schema is now `z.literal("LEARNER")`.

## SSO.9: Domain-check rate limit — flood the unauth endpoint

Without authentication, fire 100 GETs at the domain-check endpoint
within ~30 seconds:

```js
() => Promise.all(
  Array.from({ length: 100 }, () =>
    fetch("/api/auth/sso/domain-check?email=probe@example.com", {
      credentials: "omit",
    }).then(r => r.status)
  )
)
```

### Assertions
- The first ~60 responses are `200` (or 200 with `{enforceSSO: false}`).
- The remainder are `429` — the Upstash `authLimiter` covering
  unauth endpoints fires per `middleware.ts:240-246` at 60/hr/IP.

Re-run from the SAME IP within the same hour and confirm 429 persists.

**Regression guard for audit Phase B.8.** If all 100 succeed,
domain-enumeration of registered orgs is unrestricted — a public
attack surface.

## SSO.10: Role change → session refresh on next request (sessionGeneration)

Spawn a fresh test user, add as LEARNER to a test org. Capture the
user's session cookie (login via Chrome MCP).

```sql
-- Baseline: assert current role + sessionGeneration value
SELECT u.id, u."sessionGeneration", m.role
FROM users u
JOIN "Membership" m ON m."userId" = u.id
WHERE u.email = 'test-sessiongen@familiarise.test';
-- Capture <gen-before>
```

Now PATCH the role to MANAGER via the members endpoint (as Wipro OWNER):

```js
() => fetch("/api/organizations/<wipro-id>/members/<member-id>", {
  method: "PATCH", credentials: "include",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({ role: "MANAGER" }),
})
```

### Assertions
- `status === 200`
- DB:
  ```sql
  SELECT u."sessionGeneration", m.role FROM users u JOIN "Membership" m ON m."userId" = u.id
  WHERE u.email = 'test-sessiongen@familiarise.test';
  -- Expected: sessionGeneration = <gen-before> + 1, role = 'MANAGER'
  ```
- As the patched user, hit `GET /api/auth/get-session` (or any
  customSession-emitting endpoint) and assert the response's
  `user.sessionGeneration` equals the new DB value AND
  `organizationMemberships[]` shows the new MANAGER role — **without
  forcing a logout**.

Repeat for member removal (DELETE): `sessionGeneration` increments by
1, and the next session lookup omits the now-REMOVED org from the
memberships array.

**Audit Phase B.5.** Pre-fix, the user kept their LEARNER session for
up to 24h after promotion — operating with stale permissions.
