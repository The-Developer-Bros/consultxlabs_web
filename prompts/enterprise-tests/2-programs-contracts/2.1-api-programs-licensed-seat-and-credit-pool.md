## Case PR.7: ProgramAssignment is idempotent on duplicate POST

Assigning the same program to the same membership for the same
`periodStart` twice via the API returns **201 with the existing
ProgramAssignment row** (idempotent upsert), NOT a 409 conflict.
The underlying `@@unique([programId, membershipId, periodStart])` is
still enforced at the DB level — the route handles the conflict by
returning the prior row instead of erroring out.

### Steps
First POST:
```js
() => fetch("/api/organizations/<orgId>/programs/<programId>/assign", {
  method: "POST", credentials: "include",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({ membershipId: "<membershipId>", periodStart: "2026-05-01", periodEnd: "2026-05-31" })
}).then(async r => ({ status: r.status, body: await r.json() }))
```
Capture `<assignmentId>` from `body.data.id`. Then repeat the exact
same POST.

### Assertions
- Both responses: `status === 201`.
- Both response bodies have the **same** `data.id` (= `<assignmentId>`).
- DB:
  ```sql
  SELECT count(*) FROM "ProgramAssignment"
  WHERE "programId" = '<programId>' AND "membershipId" = '<membershipId>'
    AND "periodStart" = '2026-05-01';
  -- Expected: 1 row (uniqueness preserved)
  ```
- Direct SQL re-insert with the same triple still fails with P2002:
  ```sql
  INSERT INTO "ProgramAssignment" ("programId", "membershipId", "periodStart", ...)
  VALUES ('<programId>', '<membershipId>', '2026-05-01', ...);
  -- Expected: ERROR 23505 (unique_violation) — DB enforcement is intact
  ```

**Regression signal:** if the second API POST returns 409 instead of
201-with-existing, the route lost its idempotent-upsert behaviour.
Bug — most clients (especially form submissions on flaky connections)
rely on idempotent retries for assignment ops. ASK before changing.

## Case PR.8: Refund → BookingUtilization.reversedAt

Refund an existing booking:
```js
() => fetch("/api/refunds", {
  method: "POST", credentials: "include",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({ paymentId: "<paymentId>", reason: "test refund" })
}).then(async r => ({ status: r.status, body: await r.json() }))
```

### Assertions
```sql
SELECT "reversedAt", "reversalReason", "engagementsConsumed"
FROM "BookingUtilization" WHERE "paymentId" = '<paymentId>';
-- Expected: reversedAt IS NOT NULL, reversalReason set, engagementsConsumed unchanged
```

Plus a counter `UsageLedgerEntry` with negative `engagementsConsumed`.

**Regression signal:** if `BookingUtilization` row is *deleted* instead
of marked reversed, history is destroyed. NON-TRIVIAL — ASK.
