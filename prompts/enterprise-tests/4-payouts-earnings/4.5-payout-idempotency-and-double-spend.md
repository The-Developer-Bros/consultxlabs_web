# 4-payouts-earnings — Payout idempotency + double-spend guard

> **Required reading:** [`_shared/shared-setup.md`](../_shared/shared-setup.md),
> [`_shared/mcp-recipes.md`](../_shared/mcp-recipes.md),
> [`_shared/case-template.md`](../_shared/case-template.md).
> Apply the **fix-and-retest gate** when any case fails.

**Surface(s) under test:**
- `scripts/payouts/process-payouts.ts:69` — `X-Payout-Idempotency: payout_${payoutId}` (deterministic, no `Date.now()`)
- `lib/payments/payouts/org-payout-service.ts:createOrgPayoutBatch` — Redis lock + `idempotencyKey @unique` + Serializable tx
- `prisma/schema.prisma model OrganizationPayout` — `idempotencyKey @unique`, `gatewayPayoutId @unique`

**Round-3 invariant — see shared-setup §4:** "Payout idempotency — `scripts/payouts/process-payouts.ts:69` uses `payout_${payoutId}` (no `Date.now()`). `OrganizationPayout.idempotencyKey @unique`. Re-runs return `alreadyExisted: true`."

> **Booking-flow dependency.** Cases P.2–P.4 require an
> `OrganizationEarnings` row seeded from a real booking + payment +
> webhook chain. P.1 (source-grep regression guard) is unaffected and
> runs normally. Until a seed helper lands, run P.2–P.4 in
> **code-verification mode** — invoke `createOrgPayoutBatch` from a
> standalone tsx script with synthesized earnings — rather than full
> end-to-end. Tracked separately.

**Case roster:**
1. **P.1** — Source code regression guard: line 69 contains no `Date.now()`
2. **P.2** — `createOrgPayoutBatch` idempotency short-circuit
3. **P.3** — Concurrent batch creates (race on the Redis lock)
4. **P.4** — Settlement ledger never doubles for the same idempotency key

## Case P.1: Source code regression guard

Read the file directly via Bash:

```bash
sed -n '60,72p' scripts/payouts/process-payouts.ts
```

### Assertions
- Line 69 contains `payout_${payoutId}` and **does NOT** contain
  `Date.now()`.
- Line is the value of the `X-Payout-Idempotency` header.

This case exists because the original bug was a single-line regression
(commit `2c423b88` had `payout_${payoutId}_${Date.now()}`). If anyone
reverts the fix, this case fails immediately and cheaply.

If the line was reformatted (multi-line, different indentation), grep
defensively:
```bash
grep -n "X-Payout-Idempotency" scripts/payouts/process-payouts.ts
grep -nE "Date\.now\(\)|new Date\(\)\.getTime\(\)" scripts/payouts/process-payouts.ts
```
- The first grep must show `payout_${payoutId}` (and nothing else).
- The second grep must return no lines.

**Regression signal:** any `Date.now()` / `new Date().getTime()` /
`crypto.randomUUID()` in the header → NON-TRIVIAL fix (touches
payment-gateway code). ASK before reverting it.

## Case P.2: `createOrgPayoutBatch` idempotency short-circuit

Spawn a fresh host org with READY earnings (see
`4.3-tds-withholding-on-org-payouts.md` preconditions). Capture `<orgId>`.

### Steps
First call:
```js
() => fetch("/api/organizations/<orgId>/payouts", {
  method: "POST", credentials: "include",
  headers: {"Content-Type": "application/json"},
  body: JSON.stringify({
    periodStart: "<start>", periodEnd: "<end>",
    idempotencyKey: "P-2-dup-key"
  })
}).then(async r => ({ status: r.status, body: await r.json() }))
```

Capture `<payoutId>` from `body.payoutId`. Then immediately re-call with
the same idempotency key.

### Assertions
- Second response body has `alreadyExisted: true` and `payoutId ===
  <first-payoutId>`.
- DB has exactly one row:
  ```sql
  SELECT count(*) FROM "OrganizationPayout"
  WHERE "idempotencyKey" = 'P-2-dup-key';
  -- Expected: 1
  ```
- TDS withholding ran exactly once — second call did not double-deduct.
- Only one `PAYOUT_INITIATED` audit row for this org since `<start>`.
- Only one `PAYOUT_SENT` settlement entry.

## Case P.3: Concurrent batch creates (race on the Redis lock)

Fire 5 parallel POSTs with the same idempotencyKey:

```js
() => Promise.all(
  Array.from({ length: 5 }, () =>
    fetch("/api/organizations/<orgId>/payouts", {
      method: "POST", credentials: "include",
      headers: {"Content-Type": "application/json"},
      body: JSON.stringify({
        periodStart: "<start>", periodEnd: "<end>",
        idempotencyKey: "P-3-concurrent"
      })
    }).then(async r => ({ status: r.status, body: await r.json() }))
  )
)
```

### Assertions
- Exactly **one** result has `alreadyExisted: false` (or omitted —
  treat as "newly created"); the other 4 have `alreadyExisted: true`.
- All 5 `payoutId` values are identical.
- One row in DB:
  ```sql
  SELECT count(*) FROM "OrganizationPayout"
  WHERE "idempotencyKey" = 'P-3-concurrent';
  -- Expected: 1
  ```
- Some responses may carry the lock-error `PAYOUT_LOCK_CONFLICT` if the
  Redis lock acquisition timed out — that's acceptable as long as no
  duplicate row was written. Note in the run.

**Regression signal:** if any response 500s with a P2002 leak (unique
constraint violation surfacing as HTTP 500 instead of being caught and
returned as `alreadyExisted: true`), the catch block in
`createOrgPayoutBatch` is broken. NON-TRIVIAL — ASK.

## Case P.4: Settlement ledger never doubles

After P.2 + P.3:

```sql
SELECT count(*) FROM "SettlementLedgerEntry"
WHERE "payoutId" IN (
  SELECT id FROM "OrganizationPayout"
  WHERE "idempotencyKey" IN ('P-2-dup-key', 'P-3-concurrent')
)
AND kind = 'PAYOUT_SENT';
-- Expected: 2 (one per distinct payout — NOT one per call)
```

The ledger row is written inside the `createOrgPayoutBatch` transaction.
If the row count is 6 or more (5 from P.3 + 1 from each P.2 attempt),
the idempotency short-circuit is wired but the ledger write is outside
the gate. NON-TRIVIAL — ASK.
